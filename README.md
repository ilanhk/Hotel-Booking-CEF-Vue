# Hotel Booking

A web application for searching and booking hotel rooms.

- **Guests** search hotels by city, browse hotel and room-type galleries, pick dates on a booking calendar, book a room and follow their bookings.
- **Property Managers** manage the hotels assigned to them: they see the bookings made at their hotels, filter them by status or guest, then approve or reject each one (a comment is required when rejecting).

**Stack:** Vue 3 + TypeScript + Pinia + Vue Router + Axios + Tailwind CSS (frontend) · Node.js + [Common Event Framework](https://www.npmjs.com/package/commoneventframework) (backend) · PostgreSQL + TypeORM · Vitest + GitHub Actions (tests/CI).

## Project structure

```
backend/
  src/
    root.yaml                 CEF routes: URL + method -> handler
    index.ts                  CEF server entry point
    data-source.ts            TypeORM / PostgreSQL connection
    seed.ts                   Demo users, hotels, rooms and bookings
    auth/                     login, register, logout, me (+ password hashing, input validation)
    users/                    User entity, user handlers
    hotels/                   Hotel entity, hotel search, cities, "my hotels"
    hotel-images/             Hotel gallery images
    room-management/          rooms, room types (with price) and room-type images
    bookings/
      booking.entity.ts
      commands/               CreateBooking, ApproveBooking, RejectBooking
      events/                 BookingCreated / Approved / Rejected
      handlers/               thin HTTP layer: auth, validate input, call a command
    shared/                   event bus, HTTP error type, auth helpers
    test/                     test setup (DB safety guard) and factories
    generated/HandlerRegistry.ts   generated by cef-gen-handlers (do not edit)
  scripts/run-local.js        loads .env and starts the built server on PORT
frontend/
  src/
    api/                      Axios instance and API calls
    components/               Calendar, hotel list, image gallery, bookings list, pagination, dialogs
    composables/              usePaginatedList (shared table loading state)
    stores/                   logged-in user state
    router/                   routes + role-based guards
    views/                    One view per page
```

Request flow: `root.yaml route -> handler (auth + input check) -> command -> database -> event`.

Data model: a **Hotel** (city, managed by one Property Manager) has many **Room types** (name, price per night, images) and many **Rooms** (each of one room type). A **Booking** belongs to a Guest and a Room.

## Prerequisites

- Node.js 20 or newer
- A PostgreSQL database (local install, Docker, or a hosted one such as Neon)

## Setup

### 1. Database

Create an empty database, for example:

```sql
CREATE DATABASE vacations;
```

No migration is needed: the tables and indexes are created automatically on first start (TypeORM `synchronize: true`, see Known limitations).

### 2. Backend configuration

Create `backend/.env` with:

| Variable | Meaning |
|---|---|
| `PORT` | API port (default `3600`; the frontend dev proxy expects this) |
| `DATABASE_URL` | PostgreSQL connection string. Add `?sslmode=require` for hosted databases |
| `JWT_SECRET_ACCESS` | Secret used to sign JWTs. Use a long random string |
| `ACCESS_TOKEN_NAME` | Name of the HttpOnly cookie that holds the JWT (e.g. `access_token`) |
| `SEED_DEMO_PASSWORD` | Optional. Password for demo users (default `Vacation123!`) |

### 3. Install dependencies

From the project root:

```bash
npm run install:all
```

```bash
npm run seed
```

It is safe to run more than once: existing users and hotels are skipped, and hotels that already have bookings don't get more.

## Run

Start both servers with one command from the project root:

```bash
npm run dev
```

- Frontend: http://localhost:5173
- Backend: http://localhost:3600 (health check: `GET /health`)

Or run them separately: `npm run dev` inside `backend/` and inside `frontend/`.

The backend has no hot reload, so restart it after backend changes. A Guest lands on `/guest` after login, a Property Manager on `/property-manager`.

Other useful commands (from the project root):

```bash
npm --prefix frontend run build      # type-check + production build
npm --prefix frontend run lint
npm --prefix backend run codegen     # regenerate HandlerRegistry.ts after changing root.yaml
```

## Testing

The backend has integration tests ([Vitest](https://vitest.dev)) that run against a real Postgres, because the booking rules depend on SQL and SERIALIZABLE transactions. They cover overlapping and concurrent bookings, pricing from the room type, hotel search, manager scoping and role checks.

```bash
npm --prefix backend run test:db:up    # throwaway Postgres on localhost:5433 (needs Docker)
npm --prefix backend test
npm --prefix backend run test:db:down
```

The tests drop and recreate the schema, so they refuse to run unless `DATABASE_URL` points at a local database whose name contains `test`. The development database in `.env` is never touched. GitHub Actions (`.github/workflows/ci.yml`) runs lint, type-check, build and these tests on every push and pull request.

## Assumptions

The assignment leaves some points open. These are the interpretations used:

- **Two roles.** Guests book rooms; Property Managers review bookings at the hotel they manage. Approving or rejecting is restricted to Property Managers, and only for their own hotels.
- **Price lives on the room type.** All rooms of a type in a hotel cost the same per night. A booking's total is `nights x price`.
- **Check-out day is occupied.** Dates are inclusive, so a booking that ends on a day blocks another guest from checking in that same day.
- **Pending and Approved bookings hold the room.** Rejected bookings are ignored by the overlap check and search availability, so the dates can be booked again. The UI calls an Approved booking "Booked" in the calendar legend.
- **"End date must be after start date"** is read strictly: a booking must span at least two different days, and the past is not allowed.
- **Search shows hotels with a free room.** A hotel is hidden when every room is taken for the chosen dates, and shows the number of free rooms and the cheapest price.
- **Roles are assigned by the server.** Self-registration always creates a Guest. Property Managers come from the seed script.

## API

All routes are served by CEF from `backend/src/root.yaml`. Errors are JSON (`{ "message" }` or `{ "error" }`) with a proper status code: 400 validation, 401 not logged in, 403 wrong role, 404 not found, 409 conflict.

| Method | Route | Who | Description |
|---|---|---|---|
| GET | `/health` | public | Health check |
| POST | `/auth/register` | public | Create a Guest account (also logs in) |
| POST | `/auth/login` | public | Log in, sets the JWT cookie |
| POST | `/auth/logout` | any | Clears the cookie |
| GET | `/auth/me` | logged in | Current user (restores the session after a refresh) |
| GET | `/hotels/cities` | logged in | Cities that have hotels (search dropdown) |
| GET | `/hotels/search?city=&startDate=&endDate=` | logged in | Hotels with a free room for the dates, with free-room count and cheapest price |
| GET | `/hotels/:id/room-types?startDate=&endDate=` | logged in | A hotel's room types with price, images and availability |
| GET | `/my-hotels` | Property Manager | Hotels managed by the caller |
| POST | `/bookings` | Guest | Book a room `{ roomId, startDate, endDate, reason? }` |
| GET | `/my-bookings?page=&limit=` | logged in | The caller's own bookings, paginated |
| GET | `/my-bookings/booked` | logged in | The caller's Pending/Approved bookings, unpaginated (calendar) |
| GET | `/bookings?page=&limit=&status=&userId=` | Property Manager | Bookings at the caller's hotels, filtered and paginated |
| GET | `/bookings/:id` | owner guest or the hotel's manager | One booking |
| POST | `/bookings/:id/approve` | Property Manager | Approve a Pending booking |
| POST | `/bookings/:id/reject` | Property Manager | Reject a Pending booking `{ comment }` (comment required) |
| GET | `/users` | Property Manager | Guests who booked at the caller's hotels (user filter) |
| GET, PUT | `/users/:id` | self or Property Manager (GET) · self (PUT) | Read a user, change own name |

Paginated responses look like `{ data: [...], pagination: { page, limit, total, totalPages } }`. `limit` defaults to 10 and is capped at 100.

## Business rules

| Rule | Where it is enforced |
|---|---|
| End date must be after the start date (same day is not allowed) | `CreateBooking` command; the calendar also blocks it |
| A room can't be booked twice for overlapping dates (Rejected bookings don't count) | `CreateBooking` command, inside a SERIALIZABLE transaction (concurrent attempts: one wins, the rest get 409) |
| Bookings in the past are not allowed | `CreateBooking` command; past days are greyed out |
| Only Pending bookings can be approved or rejected | Approve / Reject commands use a conditional update (`WHERE status = 'Pending'`), returning 409 otherwise |
| Rejecting requires a comment | Reject command (400) and the required field in the reject dialog |
| Only the hotel's own Property Manager can approve or reject | Command scopes by hotel (404 for other hotels), role check in the handler (403) and route guard in the frontend |

## Technical decisions

- **Commands and events.** Each write is a command function (`commands/`) that validates, writes to the database, then publishes a domain event (`BookingCreated / Approved / Rejected`) on a small in-memory event bus (`shared/event-bus.ts`). Reads skip commands and query directly. Handlers stay thin: authenticate, check role, parse input, call the command.
- **Common Event Framework.** Routes live in a single `root.yaml` (`x-handler: <file>#<exportedFunction>`), and `cef-gen-handlers` generates `HandlerRegistry.ts` from it. CEF has no middleware, so each handler calls `authenticate` itself. CEF does not decode query strings, so multi-word values such as `Tel%20Aviv` are decoded in the handler.
- **Authentication.** JWT in an `HttpOnly`, `SameSite=Strict` cookie (not readable from JavaScript, so safer than localStorage). Passwords are hashed and never returned. The role is read from the database for the signed user id, never from the client.
- **Concurrency safety.** The overlap check and insert run in one SERIALIZABLE transaction. Approve and reject are single conditional `UPDATE ... WHERE status = 'Pending'` statements, so two managers acting at once cannot both succeed.
- **Tests against real Postgres.** The rules above depend on SQL and transactions, so the tests use a throwaway database rather than mocks, with a guard that refuses to run against a non-test database.
- **Same-origin frontend.** In development Vite proxies `/api` to the backend, so the cookie is first-party and no CORS setup is needed.
- **Frontend.** Role-based router guards, Pinia auth store, reusable components (image gallery, booking calendar, bookings list), a `usePaginatedList` composable that cancels stale requests, loading states on login, register and booking, and a 401 on an expired session returns the user to the login page.

## Known limitations

- **`synchronize: true`** creates and alters tables automatically. Fine for this assignment, but a real deployment should use TypeORM migrations.
- **In-memory event bus.** Events are published in-process and are lost on restart. A production version would use a broker (and an outbox).
- **Production serving.** Only the development setup (Vite proxy) is configured. A deployment needs the frontend served on the same origin as the API (for example a host rewrite of `/api/*`), and `NODE_ENV=production` so the cookie gets the `Secure` flag.
- **No refresh tokens.** The access token is short-lived, so users log in again after it expires.
- **Hotel images are external URLs.** Images are stored as URLs (Unsplash in the seed); there is no upload flow.
- **No hotel, room or price management screens.** Property Managers review bookings but hotels, rooms and prices are created by the seed script.
- **No guest cancellation.** A Guest can't cancel a booking once it is made.
- **Registration** is open and always creates Guests. There is no admin screen to create Property Managers.
- **No rate limiting or account lockout** on login.
- **Offset pagination** gets slower on very deep pages; keyset (cursor) pagination would scale better.
- **Dates are date-only** (no time zones or check-in times).
